# Private Safety Operations — implementation and deployment handoff

Status: review branch implementation with local mocked-provider tests; **not deployed or production-validated**. The public Safety offer and Product 001 are unchanged. No operating DOCX/ZIP files, client uploads, private tokens or service credentials are in the repository.

## Authentication inspection and choice

The existing student portal uses Supabase Auth with persistent sessions and private `portal-files` storage. The homepage's Teacher Mode is a local browser toggle, not a server authorization boundary. Existing `profiles` RLS lets users update their own row (including role), and enrollment administration uses a shared-key pattern. Those mechanisms are not used to authorize Safety access.

Safety reuses the existing Supabase project and session format. Each staff request is verified with Supabase `auth.getUser(jwt)`, then checked against `safety_staff`. This new allowlist can be changed only by an administrator/service role. Seed only Mike's verified existing auth UUID and specifically authorized instructor UUIDs; no user metadata/profile role or browser flag can grant access. The existing authentication/enrollment system is not replaced or modified.

The public `safety-operations.html` contains only a shell. Logged-out visitors are redirected to `safety-login.html`, which uses the existing Supabase password sign-in. Ordinary accounts see Access denied; actual library content/downloads require the backend check every time. Homepage Teacher Resources and portal receive a shortcut only after a successful server staff check. Raw document files and ZIP bytes are returned as authenticated attachments, never public static assets or public storage URLs. The bucket is private and browser roles have no object policies for it.

## Customer workflow

A separate Safety Stripe Payment Link/Price must be configured for **$499 USD one time**. Never use Product 001's $14.99 link. `checkout.session.completed` and `checkout.session.async_payment_succeeded` raw webhook events are verified by the official Stripe SDK. The service retrieves the paid session, exact Payment Link and Price, amount/subtotal, mode and payment charge from Stripe. Unpaid, wrong-product, refunded and disputed payments do not authorize intake.

A verified order enters a persistent SQLite queue. Its unique Checkout Session prevents duplicate orders. The SMTP worker sends a random seven-day private intake token to the checkout email; only its hash is stored. It retries failed email with backoff across restarts. Rare crashes after SMTP acceptance can produce duplicate invitations; recipients remain the verified checkout email. Staff can requeue an expired/missing invitation from the engagement view. Never log these links. The customer page moves the token from URL fragment into per-tab sessionStorage and removes it from the address bar; API requests use Authorization headers, not query parameters.

The customer does not need a course enrollment or a portal account. Their private token scopes access to exactly one server-verified engagement. Payment is checked again for intake/upload access. A success-page redirect, session ID or client flag cannot authorize access. Configure Stripe's success message to tell the purchaser to check email; do not link to an unprotected onboarding URL as proof of payment.

The branded onboarding page displays the scope/independence statement and prohibited-upload warning. It records representative, acknowledgment version/time and digital intake. Customers receive an on-screen confirmation only (no final report or findings are generated/sent). Their files are placed in the private Supabase client-upload bucket, under a server-generated engagement/object ID. Only staff can download submissions. Accepted uploads: PDF/DOCX, 10 MB each, maximum 20 documents, explicit allowed review category and redaction confirmation. File signatures/limited DOCX structure are checked; that is not malware scanning or automated sensitive-data detection. Keep storage isolated and use your approved malware scanner before opening untrusted files. An upload category does not prove its contents are appropriate; the client warning and manual review remain necessary.

Staff can view intake, acknowledgment, document list, and set all eight requested statuses: Paid; Intake pending; Intake received; Documents complete; Review in progress; Report ready; Findings meeting scheduled; Closed. Each status change is audited by staff user ID. No status change sends a report or makes a professional finding. Mike remains responsible for review, report approval and delivery. Client intake edits/uploads stop once the staff advances the review beyond Intake received; staff can reopen that status if corrections are agreed.

## Deployment prerequisites and sequence

1. Provision a single always-running Node 24+ service behind HTTPS with a private persistent volume for SQLite. Do not run the worker in ephemeral functions or multiple replicas. The existing Netlify lead site and GitHub Pages site remain unchanged. This new backend uses the existing Supabase private-storage provider, rather than storing binaries in the static site.
2. In the existing Supabase project, apply `storage.sql` as administrator. Confirm all pre-existing `storage.objects` policies are bucket-scoped and do not grant broad access to the two new buckets. Assign only verified owner/instructor `auth.users.id` values to `safety_staff`. Do not automatically trust the editable profile role. Ordinary authenticated users must not be able to select or alter the staff allowlist.
3. Configure secrets privately with your host's secrets manager. `.env.example` lists names only. Required: Supabase URL and server-only service-role key; Stripe restricted API key, mode, actual Safety Payment Link ID/Price ID and endpoint signing secret; verified TLS SMTP sender/credentials; HTTPS main-site origin; absolute database path outside the website checkout. All financial values must match the $499 service. No actual Safety Stripe IDs or hosting/email credentials were supplied in this task.
4. Run `npm ci --omit=dev` inside this service. Start `server.mjs` under a process supervisor with the private configuration. It verifies the Stripe link/price, confirms both storage buckets are private, and checks SMTP before serving. It has no static-file server. Configure the HTTPS proxy to redact Authorization and query data from logs, preserve raw webhook bodies, disable caches, and apply request/rate limits. The UI permits only the configured HTTPS API origin; CORS permits only `SITE_ORIGIN`.
5. Upload the supplied nine operating DOCX files and complete ZIP privately using `upload-library.mjs /absolute/private/extracted-folder` with the server credentials injected privately. The local extracted archive is called `complete-system.zip`. The source documents were extracted for this task outside every website worktree under `.codex_tmp/safety-private`. Do not add that directory to Git. The upload script checks bucket privacy, does not publish URLs, and maps all nine files into the required order.
6. Configure the deployed `/stripe/webhook` endpoint for the two Checkout events with the correct mode/secret. Use a separate Safety sandbox link/price for test-mode purchases. Do not repurpose the classroom product configuration. Confirm webhook retries work and the verified checkout email receives the intake link without needing a redirect.
7. Set `apiOrigin` in root `safety-config.js` to the actual deployed HTTPS API origin and copy it to `/docs`. Both frontend copies use the existing Supabase public project URL/publishable key, which are not secrets. Keep `apiOrigin` empty until the private backend is ready: the shortcut stays hidden and the UI fails closed with a setup message.
8. Complete production acceptance testing below, obtain Mike's review, and publish the frontend branch/PR. Do not publish private binaries during this process. Set retention/deletion policies and securely back up private database and storage together. Monitor pending invitations and SMTP bounces; `/health` only indicates process availability.

## Tests and limits

`npm test` runs eight local security/integration tests with actual Stripe signature checks and mocked Supabase/Stripe payment/email/storage responses. They cover logged-out/ordinary/authorized staff; ordered library and ZIP; required acknowledgment; private upload routing; payment mismatch and forged events; deduplication, expiry/refunds; status authorization; disallowed file types; and direct HTTP denial. They do not establish that your deployed Supabase RLS, SMTP, Stripe or hosting are configured correctly.

Before calling the production integration complete, use actual logged-out, student and authorized staff sessions to verify all eight acceptance requirements. Request private bucket public URLs anonymously and with a normal user's token and confirm denial. Test attempts to set a profile role or local Teacher Mode flag and confirm Safety access stays denied. Complete a sandbox purchase and email/intake/upload cycle, including a second customer who must not see the first customer's engagement. Test temporary SMTP failure/restart, expired invitations, duplicate webhooks, wrong product, pending payment and refund. Inspect mobile layouts. Scan changed Git files for actual credentials and private binaries. Verify all existing navigation links and public Safety site behavior. Any live charge requires explicit owner authorization.
